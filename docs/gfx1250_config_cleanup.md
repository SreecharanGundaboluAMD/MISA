# gfx1250 Config File Cleanup

User-reported discrepancy: `config/` had 317 gfx1250 files vs. 10 for gfx950.
Investigated and cleaned up.

## Why gfx1250 had so many more files

gfx950 (and every other legacy arch) has exactly one config per
(direction, precision): 10 files = 3 directions x 3 precisions (fwd/bwd/wrw
x fp16/bf16/fp32) + 1 (fwd int8). There is no combinatorial tunable search
for those archs -- one hand-tuned config per direction/precision is the
whole story.

gfx1250's WMMA pipeline accumulated files from ~70+ phases of individual
feature validation, each adding its own narrow, single-feature standalone
config (`_dbuf.config`, `_saddr.config`, `_tdm.config`, `_mtail.config`, ...)
to prove that ONE feature worked in isolation, before Phase 5-7
(`docs/gfx1250_tuning_refactor_plan.md`) unified everything into real
combinatorial per-tile files (`_128x128_all.config` etc., one per
(direction, precision, tile shape), covering every construct-validated
tunable combination). Those single-feature files were never cleaned up
after the combinatorial generator subsumed them.

## What was actually in `config/` (317 files, before cleanup)

| Category | Count | Disposition |
|---|---|---|
| Per-tile combinatorial `_all.config` (generated by `script/generate_all_configs.py`) | 27 | **Keep** -- the real deliverable |
| Legacy union `_all.config` (generated by `script/build_gfx1250_master_configs.py`, one per direction/precision incl. int8) | 12 | **Keep** -- still load-bearing, used by both benchmark scripts as an alternate candidate set alongside the per-tile files |
| int8/int4 standalone configs | 24 | **Keep** -- int8/int4 combinatorial coverage is explicitly out of scope for this session (per user direction); these are the ONLY int8/int4 coverage that exists |
| Base source files referenced by `BASE_SECTIONS` in `generate_all_configs.py` | 18 | **Keep** -- required inputs to the generator itself, not optional |
| Standalone fp16/bf16/fp32 configs with content NOT fully covered by the combinatorial files | 152 | **Keep** -- see "Real gaps found" below |
| Standalone fp16/bf16/fp32 configs whose every section resolves (via real construction, not text matching) to a kernel name already present in the combinatorial per-tile files | **84** | **Deleted** |

## Methodology

Built a redundancy checker (ad hoc, not committed as a script -- one-off
audit): for every standalone config file, parsed each `igemm_*_gtc` section
with the real `config_parser_t`, constructed the real
`igemm_gtc_tunable_parameter_t` + WMMA generator object (the same
construct-and-emit path `is_valid()` in `generate_all_configs.py` already
uses), and computed its actual resolved kernel name via `kernel.name()`.
Cross-referenced against the full set of kernel names produced by all 27
combinatorial per-tile files (built the same way). A standalone file was
only deleted if **100% of its sections** resolved to a kernel name already
present in that set -- i.e. every kernel it could ever produce already
exists, byte-for-byte, in the combinatorial file for its
direction/precision/tile. Spot-verified on one deleted file
(`igemm_bwd_gtc_gfx1250_nhwc_fp16_dbuf.config`): rebuilt both the deleted
file and its combinatorial replacement, confirmed the `..._dbuf_dstrb`
kernel body is present and identical in the rebuilt `.inc` in both cases.

Deliberately conservative: any file with even one section not found in the
coverage set was kept, not deleted, no matter how much of the rest
overlapped.

## Real gaps found (kept, not a cleanup target -- separate follow-up work)

The 152 "not fully covered" files split into two real, legitimate reasons
the combinatorial generator doesn't reach them yet:

1. **`wmma_k_tail` and `lds_row_pad` are not in `generate_all_configs.py`'s
   `FLAGS`** (only `wmma_m_tail`/`wmma_n_tail` are). Every standalone
   `_ktail*`/`_ldsrp*`/`_mntail*` config represents genuinely uncovered
   search space, not redundant duplicates.
2. **Several standalone files use a `gemm_k_per_block` other than the
   combinatorial generator's fixed 32 (fp16/bf16) or 4 (fp32)** --
   `_k2x` (64), `_kmax` (64), `_k128`, `_k256` files represent entirely
   different tile geometries not present in `BASE_SECTIONS` at all. This is
   the SAME gap flagged by the user's separate gfx950-vs-gfx1250
   tile-coverage question -- see `docs/gfx1250_tile_coverage_gap.md`.

Neither is a "clean up now" item -- both are legitimate future
combinatorial-search expansion work (a natural continuation of Phase 7),
tracked in the tile-coverage-gap doc instead of conflated with this cleanup.

## Result

- 317 -> 233 gfx1250 config files (84 deleted).
- `script/build_gfx1250_master_configs.py` and `script/build_and_filter_configs.py`
  re-run cleanly after the deletion (10696/10696 sections still pass
  assembly); `generate_all_configs.py`'s `BASE_SECTIONS` sources all still
  present (they were explicitly protected from deletion regardless of
  redundancy status).
- gfx950's 10-file structure is not a bug or a regression to fix on the
  gfx1250 side -- it reflects gfx950 genuinely having no combinatorial
  tunable search; gfx1250's file count, even post-cleanup, is legitimately
  larger because the underlying WMMA pipeline has ~14 real tunable
  dimensions searched combinatorially, not because of file-count bloat.
